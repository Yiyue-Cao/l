# 十六个 run 驱动的分工

## 先区分驱动与交易策略

这些run文件都是可复用的实验组织程序。它们读取基础配置或精确配置清单，安排参数、日期、策略动态库与输出，再调用runner。相应so负责交易事件中的决策。不同驱动可能最终加载同一个so，也可能用通用接口加载一组策略。

下面按二进制业务符号、参数写入字符串及同包README/run.sbatch综合解释。它描述通用能力，不列未恢复的历史实际参数值，也不把支持的每条分支说成该次实验都运行过。

## 商品策略驱动

**run_comm** 为基础comm型实验提供组合生成与运行入口。核心仍是基础配置加逐组合覆盖，随后使用公共fb_sweeps启动逻辑。不能仅从run_comm这个文件名推断so恰好是哪一版本，动态库参数也属于实验身份。

**run_comm3** 对应带LOW/HIGH执行配置的comm分支，支持启动层传入指定信号子集。它承担参数写入和组合命名，真正的maker旧单保留、撤换与数量判断仍在策略库。

**run_comm4** 在基础驱动之外加入watcher配置和阶段开关。因此一次组合不应只理解成一个正式策略配置，还包含观察对象及其动态库。正式腿和观察腿的身份、账户名与发布键需要保持一致。

**run_comm5** 继续使用comm4类型的启动入口，但可以用binary覆盖选择本驱动。它新增XS数据路径、EWMA配方和信号变体等参数接线。启动脚本要求EWMA配方显式冻结，不能依赖某个构建时的隐式默认来复现历史任务。

**run_comm_maker1** 构造普通与LOW阈值、maker报价和等待/撤单相关组合，并同时写入框架顶层与custom策略字段。其被内联的逐组合配置函数已专门补充恢复，详见[专文](04_run_comm_maker1的完整作用.md)。

**run_comm_mock** 为观察型comm实现提供通用运行入口，支持信号子集。它与正式腿配合时应特别注意liquidity_consumption等框架配置；mock角色不是靠库文件名自动决定的。

## 指数、报价与低频驱动

**run_takermaker** 服务TM类型实验，支持指定信号集合，并可按顺序读取多个sweep overlay。启动层把相应配置送到驱动，由它生成具体策略配置，而不是让策略so直接读取driver-only的网格段。

**run_signalmaker** 服务SM类型实验，也支持信号集合、overlay及特定数据预检查控制。它不是sm1的唯一固定别名；最终策略身份还需要动态库与基础配置共同确认。

**run_sm3_1** 为sm3_1的主辅信号与门控实验提供专门入口。driver-only的sm31_sweep配置与so消费的custom配置处于两层，复现时需要知道驱动如何展开和写入，而不是只保存门控字段名。

**run_lowfrequency** 对应低频目标执行实验。驱动负责生成任务参数和启动回测，目标创建、截止时间、尝试次数槽与完成进度等状态仍由LF策略执行路径维护；LF4 当前二进制的重试不递增次数槽，详见其最新同名文档。

**run_fillprob** 与libfill_prob_probe.so配套，面向成交/命中概率探测相关实验。它是研究执行行为的探测组件，不能直接与方向交易策略的盈亏逻辑等同。具体观测量、输出条件和采样参数以该探测库的反编译为准。

探针库的目标价舍入、旧仓处理、特征记录和输出条件已单独整理，见[成交概率探针说明](09_成交概率探针与交易策略的区别.md)。

## 观察收益与多段策略驱动

**run_sos** 对应SoS类通用扫描。启动脚本对sos类型明确要求watcher三项配置，且支持信号子集及sos_sweep overlay。它把正式策略和观察策略组合起来启动，具体section切换仍在so中完成。

**run_sos5_phase** 更专门地组织SoS5阶段实验。共享说明要求逐信号SoS5正式配置和TM5观察配置目录，并扫描阶段门槛配方与初始资金。资金覆盖只作用于SoS5正式腿，观察腿资金保持冻结；可选阶段轨迹输出是解释状态转移的辅助证据。

其实际配置覆盖与正式/观察腿延迟检查，另见[SoS5阶段驱动专文](08_SoS5阶段驱动如何组织对照实验.md)。

## 多策略与组合矩阵驱动

**run_multistrategy** 提供多策略实验入口。阅读它时应关注生成了多少配置/动态库配对、如何命名各账户与策略，以及是否进入同一个runner，不能只数启动了多少个so文件。

**run_config_matrix** 读取冻结的精确策略配置清单，不重新枚举策略参数。它有清单加载、成员验证、案例分片、逐日审计、CSV合并和HDFS发布函数。v2支持两条正式腿共享Exchange，并能为相应正式腿附加观察腿。

其load_member还检查正式腿必须是real、开启流动性消耗，并关闭详细logger；观察腿须为mock、关闭流动性消耗，且账户名与正式腿声明的watcher账户一致。配置中的signals必须含对应abtype。存在清单资本约束时，还比较init_cash与清单资本，并检查margin_cushion_leverage_rate为1。这些是该矩阵驱动的输入契约，不能推广成所有run驱动都无条件采用同一限制。具体证据见[成员加载与验证](../../04_通用程序/反编译/run_config_matrix/decompiled_repaired/0000000000085660.c)。

**run_meta_portfolio_matrix** 读取组合案例和分配解，验证它们的血缘、日期和路径，构造组合资本与slot清单，再运行Meta runner。它具有独立的案例选择、确定性分片、输入哈希和发布血缘逻辑。组合资本控制发生在策略之上，不能只靠某个so内的净仓上限理解全局风险。

## 如何选取证据而不是凭名称猜测

判断一个实验，至少要知道具体driver、runner、so哈希、基础配置、overlay/精确清单、日期和输入路径。只说“用了comm5”或者“运行run_signalmaker”都不足以唯一确定实验。

通用README可以解释设计意图，run.sbatch解释实际传参契约，反编译解释二进制中的实现。三者如果不一致，应记录差异，而不是自动以其中一个覆盖另外两个。当前材料尚未给出加密配置明文，因此本批不声称重建了某个历史实验的全部参数。

可在[通用程序分析目录](../../04_通用程序/反编译)按文件名查看对应符号、目标函数清单、伪代码和导出日志。完整汇编与Ghidra工程保存在远端同名目录。
